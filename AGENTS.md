# AGENTS.md

## 1. Role

dsh-assistant (`@starsharryzhu/dsh-assistant`) is a general-purpose chat agent for DeepSeek Harness built on a parent-agent + worker sub-agent architecture, designed to be usable by people who know nothing about AI. Its Assistant row in the left sidebar leads straight to an assistant's conversation, which opens in the host's own conversation view; the conversation's title is a menu that switches to another assistant or creates one (a name, what it should call you, and a workspace folder it must choose), and two tabs sit right after Trajectory: IM (the WeChat connection) and that assistant's own settings. The conversation runs on a hidden router preset: it talks, records simple information itself with narrow tools over fixed files, and delegates the rest (after DeepSeek's Super-agent design and the MIT `dsh-superagent-prototype`), while background workers on a hidden worker preset do the work through the complete-subagent sub-plugin, on a model the router picks from those the user ticked, and whose write-access requests the router reviews. Around that: automatic compaction at a configurable share of the context window, a model and reasoning effort each conversation's composer chooses, an RMB balance reminder with configurable wording, a self-correcting persona and a profile per assistant holding their own time zone, a `ddl.md` schedule with repeating items, a host-side week view, a heartbeat that wakes the assistant for its reminders, its daily brief, wake-ups it set itself, and on its own every so often, instead of the host's automation tasks, daily and temporary quiet hours, lists, memos, logs, and project files, a watchdog for stalled turns and workers, tool isolation in both directions, and WeChat through the im-robot sub-plugin: the model chooses with `im_route` whether each turn's reply also goes to WeChat, and what they send lands in the workspace's chat inbox `IM/WeChat/`, kept for a set number of days, with images and files shown in the conversation. Assistant conversations stay out of the host's session lists. It supports only DeepSeek Harness Desktop `>=0.2.1-rc.5 <0.3.0`, verified on macOS with the real app and model on 0.2.1-rc.5 and 0.2.2-rc.1.

## 2. Constraints

- Never modify the harness checkout; everything is plugin code. The only host behavior changed is the preset registry's `list()`, wrapped on its prototype while the plugin is loaded so both hidden presets stay out of every preset list.
- Assistant conversations use the host's conversation view (the user's choice, 2026-11-01, over the earlier self-drawn one), so other plugins' changes to that view reach them; tools stay isolated on the host side. The composer's permission picker is hidden there and the router's policy re-pins the permissions to what the assistant's IM tab chose (workspace write by default, never asking); the model and effort pickers work in the composer and the IM tab alike, and each conversation keeps its own choice in its session history (the user's choice, 2026-11-03, replacing a fixed model in the settings).
- Tool isolation: this package registers no global tool; its sub-plugins serve only the two hidden presets (`presets` settings); each preset's policy denies every other global tool (a deny list, because an allow list also masks the preset's own tools).
- The router preset has no general file writes, no shell, no web, and no official subagent tool; it writes only through the record tools (`src/host/records`), each bound to fixed files in its user's workspace. It never asks questions except to approve a worker's access or for a worker's one decision, in plain words, never through a question tool.
- The record tools register in the hidden presets' scope, never as global tools, so normal sessions neither see nor can call them.
- Workers run only the models the user ticked: the settings row hands the list to complete-subagent (`ownModel: false`), which never offers the conversation's own model unless ticked; nothing else is pinned.
- Sub-plugins are npm packages pinned to exact versions in `dependencies` and mounted by the group row; a standalone install of the same plugin switches the bundled copy off through each child's `disabled: !!js` guard, which the Loader evaluates at every mount decision. A profile that writes its composed tree back into its root `cordis.yml` can store that guard as a fixed `true`; the group plugin drops a literal `true`, which the patch never sets (verified in a scratchpad host with and without a standalone copy).
- The settings row is the channel between the page and the host (assistant list, WeChat requests and states); it must stay a top-level row.
- Runtime imports: `@deepseek-ai/cordis`, `@deepseek-ai/schemastery`, `@deepseek-ai/dsh-tools`, Node built-ins, and lazily `@deepseek-ai/dsh-app-boot`; the browser half uses only the page's shared modules and the vendored QR library.
- Only DeepSeek Harness Desktop `>=0.2.1-rc.5 <0.3.0` is supported (the user's choice, 2026-11-03), and the two sub-plugins carry the same range. No manifest field can enforce the app: `dsh.bundle.platforms` names operating systems and `dsh.client.platform: web` is the page runtime Desktop uses too, so the README and the npm description state it.
- Package identity: `@starsharryzhu/dsh-assistant` `0.2.1`, MIT, `engines.dsh` `>=0.2.1-rc.5 <0.3.0-0`; `tests/patch.test.ts` pins them. The npm package name is `PACKAGE_NAME`; the internal id `dsh-assisstant` (`PLUGIN_ID`: the settings namespace, preset ids, panel id, and data folder) keeps the original spelling so settings and conversations stored by earlier local installs survive the rename. The floor is the oldest host actually run: rc.3 and rc.4 are untested.
- Host services differ across that range: see the constraints in `src/host/AGENTS.md`. Specs with fakes cannot show a host has a method; check the packaged host (the `@deepseek-ai` packages inside the Desktop app's `app.asar`).
- `lib/` is generated by `node build.js` and committed, because `link:` and git installs do not build. Rebuild it only while no host runs this package through `link:`, or restart that host right after: at its next profile write a running host compares loaded modules with disk, replaces this plugin (a QR code then reads as expired), and writes its composed tree into the profile's root `cordis.yml`, whose rows win over bundle patches at the next boot. Test in a copy meanwhile.
- Host writes to the settings row go through `SettingsWriter`, which leaves the HMR service's transaction storage: a write set off by a settings change otherwise fails with "HMR transactions cannot be nested" forever, since the storage follows every async continuation. It writes with `settings.mutate`, which replaces each field: `settings.update` merges plain objects recursively, so a key dropped from one would stay.
- The Plugins page holds the settings every assistant shares; each assistant's settings tab holds its own, stored on its entry in the assistant list. The user drew that line (2026-11-02): models, compaction, balance, and persona limits are shared; schedule, watchdog, and WeChat are per assistant.
- An assistant has no default folder: the create form requires one, and the host creates no conversation for an entry without one.
- A new assistant greets first (one model call): the host's view shows a session without a turn as a blank page with no title or tabs, and its composer refuses input unless the folder is a registered workspace.
- Everything timed comes from the heartbeat in the settings row; this package creates no automation task in the host, and removes what earlier versions left there at startup (the user's choice, 2026-11-05). Timed reminders are woken exactly by the host, not left to the model; `wake_after` is for what has no place in the schedule.
- Quiet hours are enforced by the host as well as the prompt: nothing proactive fires inside them, and only a turn holding a message from the user may change them or the daily brief's time (the user's rule, 2026-11-05).
- The user's time zone is the profile's `Time zone`, never the browser's or the device's (the user's choice, 2026-11-05): the model works it out from what they say and their schedule. This computer's zone stands in only until one is recorded.
- The patch and `lib/` must not change on disk while a host runs this package through `link:`: see `lib/` below.
- Text only the model reads is in English (the user's choice, 2026-11-03): its own files, tool results, worker reports, system notes. Text the user sees stays in their language: replies, the `/ddl` week view, tool-card titles, reminders, schedule titles, lists, memos, and logs. See the constraints in `src/host/records/AGENTS.md`.
- Every folder carries this four-section English file; `tests/agents-md.test.ts` enforces it.

## 3. Contents

- `src` — plugin source: the settings row, the sub-plugin group, the policy, the compactor, host modules, prompts, shared shapes, and the browser half.
- `tests` — vitest specs with fake host services and the built browser half under jsdom.
- `scripts` — the development toolchain linker.
- `locale` — Plugins page title and description in Chinese and English.
- `lib` — generated build output (committed).
- `build.js` — type-check, emit the host half and prompts, bundle and self-check the browser half.
- `cordis.patch.yml` — the bundle patch: settings row, sub-plugin group, router preset, worker preset.
- `package.json` — identity, pinned sub-plugins, peers, engine range, entries, and the browser half.
- `tsconfig.json` — host type-check settings.
- `tsconfig.build.json` — host emit settings for `lib/`.
- `tsconfig.client.json` — browser half compile settings.
- `vitest.config.ts` — test runner settings, with `DSH_HOME` in a fresh temporary folder so no spec writes to the real one.
- `README.md` — user documentation, English by default; `README-zh.md` is the Chinese version.
- `THIRD_PARTY_NOTICES.md` — notices for vendored third-party code.
- `.gitignore` — ignores dependencies, browser compile output, and local notes, keeps `lib/`.
- `.github/workflows/publish.yml` — tag-driven npm publish through trusted publishing.
